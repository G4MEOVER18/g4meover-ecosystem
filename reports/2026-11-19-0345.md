## Geliefert

- **Ideen-Recherche: ProtoView — B4B1-Dekoder (PT2262/SC5262), Sync-Suche durchläuft nur die
  Hälfte der deklarierten Muster.** `sync_patterns[]` deklariert sechs Präambel-Varianten
  (30/31/32-`te`-Gap, je mit folgendem Datenbit 0 oder 1), die Such-Schleife läuft aber nur
  `for (j = 0; j < 3; j++)` — Index 3–5 sind toter Code, werden nie geprüft. Per
  `git log -p -- protocols/b4b1.c` auf Commit `cc32c5e` ("b4b1: more robust message detection")
  zurückgeführt: das Array wurde bewusst von drei auf sechs Einträge erweitert, die
  Schleifengrenze dabei nicht mitgezogen. Gegenprobe im selben Quellbaum:
  `protocols/tpms/toyota.c` löst exakt dasselbe Muster korrekt über eine NULL-terminierte Liste.
  Fund trifft im Mittel rund die Hälfte aller realistischen Empfangsfälle (Gap-Länge und erstes
  Datenbit variieren beide unabhängig vom Nachrichteninhalt), kein konstruierter Randfall.
- Minimal-invasiver Patch (`ideas/protoview-b4b1-decoder-sync-loop-bound-fix/b4b1_c.patch`, eine
  Zeile: `j < 3` → `j < 6`). Gegen zwei frische, unabhängige Zweitkopien von `antirez/protoview`
  per `git apply --check`/`git apply` UND per `patch -p1 --dry-run`/`patch -p1` verifiziert,
  Ergebnis laut `md5sum` in beiden Fällen und beiden Prüfmethoden byte-identisch.
- Host-Repro (`ideas/repro-protoview-b4b1-decoder-sync-loop-bound-fix/`): Sync-Suche wörtlich in
  ALT/NEU extrahiert, Bitmap-Primitiven wörtlich aus `signal.c` übernommen. Für jedes der sechs
  deklarierten Muster eine eigene Bitmap gebaut: ALT findet nur Index 0–2 (Finding reproduziert),
  NEU findet alle sechs; Gegenprobe mit nullgefülltem Puffer von beiden abgelehnt (kein
  Falsch-Positiv-Risiko); `numbits < 30`-Wächter bleibt für beide wirksam. Unter
