## Geliefert

- Fund in `flipperbridge/flipperbridge.py::FlipperBridge.storage_send()`: der abschließende
  MD5-Soll/Ist-Vergleich berechnet `want` unbedingt aus den tatsächlichen Daten (für eine leere
  Datei: `hashlib.md5(b"").hexdigest()`, nie ein leerer String), setzt `got` für `data == b""`
  aber explizit auf `""` (offensichtlich um für eine leere Datei gar kein `storage md5`-Kommando
  abzusetzen) — der Vergleich `want == got` kann für jede leere Datei nie zutreffen, unabhängig
  vom tatsächlichen Geräteverhalten. Jeder Upload einer echten 0-Byte-Datei (leeres Platzhalter-
  Capture, absichtlich leere Marker-/Log-Datei, versehentlich 0 Byte große lokale Datei) wird
  damit garantiert als "FEHLER" gemeldet und mit Exit-Code 1 beendet, obwohl der vorherige
  `Ready`-Handshake und das Schreiben selbst unverändert korrekt durchlaufen und auf dem Gerät
  eine korrekte leere Zieldatei entsteht.
- Fix: für `data == b""` wird jetzt direkt `True` zurückgegeben (nichts zu vergleichen, Ready +
  Schreiben sind in diesem Fall bereits der ganze Erfolgsnachweis), ohne das `storage md5`-
  Kommando überhaupt abzusetzen — genau die Absicht, die das bisherige `if data else ""` schon
  erkennen ließ, nur ohne den unvergleichbaren Hash-gegen-Leerstring-Vergleich. Für jede
  nicht-leere Datei bleibt der Kontrollfluss identisch zum Status quo.
- `app-improvements/g4meover-companion/flipperbridge-empty-file-send-false-negative-fix.md`
  angelegt (Was, Nutzen, betroffene Dateien, Patch, Host-Repro, Testhinweis, Risiko, Quelle) samt
  `connective-patches/flipperbridge_py.patch` (unified diff, 3 Zeilen Hinzufügung/2 Löschungen),

- Host-Repro: transkribiert ausschließlich den Verifikationsschritt (ALT/NEU) über eine
