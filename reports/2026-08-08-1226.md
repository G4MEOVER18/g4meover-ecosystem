- `RollJam` (eigenes Repo) frisch geklont und Quelltext durchgesehen (`rolljam_app.c`,

  (180 ms Jam / 80 ms RX, README als Referenz), für autorisierte Tests am eigenen
  Fahrzeug/Empfänger.
- Bug in der Capture-Steuerung gefunden: `rj_run_jam_capture_phase()` ruft bei
  *jedem* Wechsel von JAMMING zurück zu CAPTURING (also bei jedem der wiederholten
  80-ms-RX-Fenster innerhalb einer Phase) `rolljam_capture_start(app, sig)` auf.
  Diese Funktion setzt unbedingt `sig->count = 0; sig->ready = false;` — sie
  unterscheidet nicht zwischen "neue Aufnahme in dieser Phase beginnen" (nur beim
  ersten Fenster sinnvoll) und "nach einer Jam-Pause weiterlauschen" (der eigentliche
  Zweck der Interlacing-Schleife). Dadurch werden in früheren RX-Fenstern derselben
  Phase bereits empfangene Flanken bei jedem weiteren Zyklus verworfen — ein
  Fabrikat, dessen OOK-Frame länger als ein einzelnes 80-ms-Fenster ist (Präambel +
  mehrere Wiederholungen, bei vielen Fahrzeugsystemen 100–300+ ms), kann so praktisch
  nie vollständig erfasst werden; die Phase läuft stattdessen häufig ins
  9-Sekunden-Timeout, weil `sig->count` nie über das hinauswächst, was ein einzelnes
  Fenster zufällig eingefangen hat.
- Mit einem host-kompilierbaren Reproduktionsprogramm (reine Zustands-/
  Pufferverwaltung auf Fensterebene, ohne RF/Hardware) nachvollzogen: nach zwei
  simulierten RX-Fenstern (10 + 10 Flanken, Stille erst im zweiten Fenster) bleibt der
  alte Code bei `count=10, ready=0` hängen (verwirft Fenster 1 beim Neustart von
  Fenster 2), während die neue Pause-/Resume-Logik korrekt auf `count=20, ready=1`
  akkumuliert. Programm kompiliert und lokal ausgeführt, Ausgabe stimmt mit der im
  Dokument angegebenen erwarteten Ausgabe exakt überein.
